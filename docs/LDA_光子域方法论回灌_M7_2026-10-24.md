## 0. 结论先行

规划写 M7 要做三件事：① 给 153 个模块做结构扫描出三张清单；② 按 A/B 清单补
`ANCHORABLE` 声明；③ 把 F-11 的证据分档用到光子侧。

**做完第一步之后，第二步被否掉了 —— 而且是被实测数据否掉的，不是我改主意。**

| # | 规划的判断 | 实测 | 处置 |
|---|---|---|---|
| 1 | 光子侧 153 模块**缺**可锚性纪律 | **纪律在锚层，不在模块层**。账本 531 道锚的 `golden_fn` **全部**落在 `lda_harness`（70/70 模块），153 个能力模块**零引用** | 不照搬 |
| 2 | A 清单 = 待补声明对象 | A 是**形态判据**（有数值闭式），`lda_l2` 多数是**设计函数**（反解几何、扫参数域），本就不该出锚 | 不补 |
| 3 | B 清单批量标 `ANCHORABLE=False` | 实测：`ANCHORABLE` 已被 `capability_modules()` 复用为**能力层名单信号** ⇒ 批量标会让 G7 从 **0 缺口变 96 缺口**（当场判红） | 不做 |
| 4 | C 清单可能发现"做了但没出锚" | C ≡ A（结构必然，因为零引用） | 改判据 |
| 5 | 第三步：光子侧扰动响应分布 | **光子 6 / 量子 8**（1.35% vs 11.43%）⇒ M6 的价值主要在**量子侧**，与规划猜测相反 | 如实记录 |

**真正找到的缺口只有两个**（都不是规划预想的那个）：

- **`lda_agent` 从未进过可达性扫描面** —— 53 模块 / 156 个公开函数对"防腐烂"完全不可见。
  补入后一次性暴露 **2 条**零引用（95 → 97）。**"没人看"和"零死函数"是两件事。**
- **成对实现只有惯例、没有机制** —— 12 个模块里同时写了闭式与独立数值两半（= 天然锚候选），
  它们各自都有门禁，但这条依赖是**命名惯例**。已立成契约 **G11**（+ G11b 双形态反向）。

## 1. 结构扫描：三张清单（`scripts/photon_anchorability_scan.py`）

### 1.1 最硬的一个事实：锚层与能力层是**两个不相交的世界**

```
账本 541 道锚
  ├─ 531 道有 golden_fn，分布在 70 个模块
  │    └─ **70 / 70 全部在 lda_harness**（`_batch_b*_numeric.py` 52 个 + 具名锚模块 18 个）
  └─ 10 道无 golden_fn 对象 = **E1–E10**（实测/经验锚，`candidate_class=None`，本就不走闭式路线）

能力层 153 个模块（lda_l2 100 + lda_agent 53）
  ├─ 被账本直接引用的：**0**
  └─ 声明 ANCHORABLE 的：**0**
```

这不是"光子侧偷懒"，而是**组织形态不同**：

| | 量子侧（`lda_qeda` 49 模块） | 光子侧（`lda_l2`+`lda_agent` 153 模块） |
|---|---|---|
| 锚的 golden 在哪 | `lda_harness`（71 道锚全在） | `lda_harness`（131 道锚全在） |
| 能力模块与锚的关系 | 模块**就是**被判定的对象 ⇒ `ANCHORABLE` + `why_not_anchored()` 自然有意义 | 模块是**设计期模型**；锚是独立的双方法对拍 ⇒ 模块层声明 `ANCHORABLE` **没有对象** |
| 纪律落在哪 | 模块声明面 | **锚层**：`DEAD_BASELINE` 的 `ANCHOR_GOLDEN_ORPHAN` / `ANCHOR_PAIR_UNREFERENCED` 分类 |

🔴 所以"给 153 个模块补 `ANCHORABLE`"= **把一种组织形态的纪律，平移到一个它不描述的位置**。
补出来的声明不会增加信息量，只会增加"看起来合规"的面积。

### 1.2 三张清单（+ 我加的第四张）

| 清单 | 判据 | 条数 |
|---|---|---|
| **A** | 有「数值闭式**形态**」但无 `ANCHORABLE` 声明 | **61** |
| **B** | 无闭式形态（纯工程 / IO / 编排） | **92** |
| **C** | 有闭式形态但账本**零引用** | **61**（C ≡ A） |
| **D** | **成对实现**（同模块内闭式 + 独立数值） | **12 模块 / 23 对** |

**A 的判据是形态，不是可锚性**：顶层公开函数 ∧ 返回数值表达式 ∧ 无 IO 调用。
`lda_l2` 里绝大多数命中项是 `qs_m5.odmr_lorentzian`、`oi_m5.bw_at_l_ghz` 这类
**设计函数**——它们回答"这个参数下性能多少"，本就不该出锚。
把 A 当"待补声明名单"，会制造 **61 条合规装饰**。

**C ≡ A 是结构必然**：既然 153 个模块零引用，"有闭式但零引用"与"有闭式"就是同一个集合。
规划把 C 当成"可能发现真问题"的清单，前提（有闭式且部分被引用）在光子侧不成立。

### 1.3 D 清单才是可行动的（12 模块 / 23 对）

| 模块 | 对数 | 门禁 | 真拿到模块？ | 在 CI core 里跑？ |
|---|---|---|---|---|
| `lda_l2/qs_m5.py` | 5 | `run_qs_m5_smoke.py` | ✅ | ✅ |
| `lda_l2/qs_m3c.py` | 3 | `run_qs_m3c_smoke.py` | ✅ | ✅ |
| `lda_l2/qs_m6.py` | 3 | `run_qs_m6_smoke.py` | ✅ | ✅ |
| `lda_l2/qs_m9.py` | 3 | `run_qs_m9_smoke.py` | ✅ | ✅ |
| `lda_l2/qs_m3.py` | 2 | `run_qs_m3_smoke.py` | ✅ | ✅ |
| `lda_l2/qs_m0 / qs_m4 / qs_m7` | 1 ×3 | 各自 `run_qs_m*_smoke.py` | ✅ | ✅ |
| `lda_l2/oi_m3.py` | 1 | `run_oi_m3_smoke.py` | ✅（`importlib.import_module`） | ✅ |
| `lda_l2/eic_behavioral.py` | 1 | `run_eic_behavioral_smoke.py` | ✅ | ✅ |
| `lda_l2/ps_m2.py` | 1 | `run_ps_m2_smoke.py` | ✅ | ✅ |
| `lda_agent/ring_loop.py` | 1 | `run_ring_double_verify_smoke.py`（**按功能命名**） | ✅ | ✅ |

**为什么 D 是真信号**：模块里同时有闭式和独立数值两条实现，说明作者**已经把
golden 与 candidate 两半都写好了** —— 那正是锚的定义。它不需要"补声明"，
它需要的是**"这对实现有人验"**。

扫描时抓到两个可疑点，逐个查清后都不是缺陷，但暴露了判据本身的漏洞：

1. **`oi_m3` 一开始被判"没 import"** —— 它用的是
   `_M3 = "lda_l2.oi_m3"` + `importlib.import_module(_M3)`。
   第一版 AST 判据只认 `import` / `from ... import`，**漏报**。
2. **`ring_loop` 一开始被判"零门禁"** —— 它的门禁按功能命名
   （`run_ring_double_verify_smoke.py`），不叫 `run_ring_loop_smoke.py`。

两处都修了判据/补了映射，**没有把它们写成"豁免"** —— 豁免是藏缺口的地方。

## 2. 为什么**不做**规划第二步：实测证据

规划第二步写"**B 类批量标 `ANCHORABLE=False`**"。这条路会直接撞墙：

```
`reachability_registry.capability_modules()` 的判据是「源码是否含 `^ANCHORABLE =`」
  ⇒ 给 92 个 B 类模块加 ANCHORABLE=False，它们**自动变成能力层模块**
  ⇒ `lock_contract()` 要求每个能力层模块至少一个入口在 MUST_BE_REACHABLE
  ⇒ 实测（本版当场跑）：
        现状            modules= 11  uncovered= 0
        批量加声明后    modules=107  uncovered=96   ⇒ **G7 立即判红**
```

要让它变绿，只有两条路：

| 路 | 后果 |
|---|---|
| 写 96 条 `CAPABILITY_MODULE_EXEMPT` 豁免 | 豁免表 96 条 ⇒ **G7 从此没有判别力**（豁免就是藏缺口的地方） |
| 给 96 个模块各锁一个入口进 `MUST_BE_REACHABLE` | 锁定面从 28 条涨到 124 条，其中 96 条是**为了过门禁而写的**，不是因为有消费者 |

两条都让"契约完整性"这个指标贬值。**所以不做。**

### 2.1 根因：`ANCHORABLE` 一个字段干了两件事

| 它被当成 | 谁在用 | 语义 |
|---|---|---|
| ① 能力层**名单**信号 | `capability_modules()` → `lock_contract()` → G7/G9 | "这个模块属于能力层，必须有反向锁定" |
| ② **可锚性裁决** | 量子侧 `why_not_anchored()` / 各模块门禁 B 组 | "这个模块的能力能不能立成锚，为什么不能" |

两者**不是一回事**，但共用一个字段。批量补声明之所以有害，正是因为它把 ① 扩张到了
92 个本不属于能力层的工程模块上。**这是 M7 挖出来的最深一条**：一个字段承担两个语义，
任何"统一补一下"都会污染其中一个。

**处置**：本版**不改** `ANCHORABLE` 的语义（改语义会动 11 个模块 + G7/G9 判据 + 3 小时基线，
风险与收益不成比例），改为**把这条语义冲突写进文档与代码注释**，
并在 `paired_implementation_modules()` 的注释里明确"量子侧用 ANCHORABLE，光子侧用成对实现契约，
**机制不同不混用**"。

### 3.1 `lda_agent` 进可达性扫描面（唯一真盲区）

```python
# lda/lda_harness/reachability.py
DEFAULT_TARGET_DIRS = ("lda/lda_qeda", "lda/lda_l2", "lda/lda_harness",
                       "lda/lda_webui", "lda/lda_agent")   # ← 本版补入
```

| 项 | 补入前 | 补入后 |
|---|---|---|
| `target_files` | 328 | **382** |
| `public_total` | 3,420 | **3,576**（+156） |
| `dead_total` | 95 | **97** |
| 新增零引用 | — | `drc_fix_loop.py::demo_fix` · `inverse_design.py::list_designs` |

🔴 **数字上升不是退化**：这 2 条本来就存在，只是此前**没有任何机制看得见它们**。
按纪律登记（`PUBLIC_API_NO_CONSUMER`），不为让数字好看去删代码，也不假装不存在。

`list_designs` 顺带暴露一条小边界：`/api/inverse_design` 端点存在，但它只跑 demo，
**没有暴露可用目标清单**。本版**不接线**（改端点响应会动端点契约与 158 个端点的快照），
只在 `DEAD_BASELINE` 的注释里写明。

### 3.2 成对实现契约 G11（把惯例变成机制）

`run_reachability_smoke` 判据 **20 → 22**。G11 是**三层递进**判据，缺一层都能被绕过：

| 层 | 要求 | 可以被什么绕过（缺这层时） |
|---|---|---|
| ① | 门禁文件**存在** | — |
| ② | 该门禁**真拿到**该模块（AST 判据） | 一个空的 `run_x_smoke.py` |
| ③ | 该门禁**真在 `CORE_SMOKES` 里跑** | 一个写了但**永不被执行**的门禁文件 |

实测 **12/12 三层全满足**（含在 CI 里跑），所以这条**起步即绿**，作用是棘轮。

- **G11b 反向三形态**（先证能变红，三形态各一例）：
  - 门禁文件**不存在** ⇒ 落进 `ungated`
  - 门禁文件**存在但不 import 该模块** ⇒ **同样**落进 `ungated`
  - 门禁存在 ∧ 真 import ∧ 但**从 CI 清单里摘掉** ⇒ 落进 `not_in_core`
    （第三形态用**真模块 + 裁剪后的真 core** 来探，不造假文件 —— 探的是判据，不是我喂对了假数据）

**判据接受三种结构性证据**（`import` / `from ... import` / `import_module` 参数位置，
含先赋给模块级常量再传入的写法），**刻意不认「文档字符串里出现模块名」** ——
`run_oi_m3_smoke.py` 的 docstring 里就有 `lda_l2.oi_m3`，认它等于让任意门禁写一句注释就过。

## 4. F-11 第三步的答案：光子侧 6 / 量子侧 8

规划问：「光子 452 条锚的 `PERTURBATION_RESPONSE` 分布是多少？如果光子侧大量依赖扰动响应，
M6 的价值比现在估计的更大。」

**答案与猜测相反：**

| 域 | strict 锚 | `RESIDUAL_NONZERO` | `PERTURBATION_RESPONSE` | 弱证据占比 |
|---|---|---|---|---|
| 光子（B1–B452） | **444** | 438 | **6**（`B10 B73 B74 B79 B87 B88`） | **1.35%** |
| 量子（B453–B525） | **70** | 62 | **8**（`B473 B474 B481 B485 B487 B489 B490 B495`） | **11.43%** |
| E/S 前缀 | 5 | 5 | 0 | 0 |
| 合计 | **519** | 505 | **14** | 2.70% |

**量子侧的弱证据密度是光子侧的 8.5 倍。** 原因在 M6 已经查实：量子段的锚常落在
"物理上不可标定"的区间（`B10` 的 `|L|·t ≈ 2.5e-4` ⇒ 残差恒 1.11e-16），只能退到
扰动响应；光子的解析/数值对拍大多能拉开真实残差。

⇒ **M6 的价值主要在量子侧，光子侧基本不需要它。** 这条反过来支持 §2 的判断：
两个域的纪律形态本来就不同，不该互相套用。

## 5. 四条可迁移方法论：逐条对照

规划说"只回灌四条可迁移的方法论"。逐条给出**光子侧的落地状态**：

| 方法论 | 量子侧形态 | 光子侧现状 | 本版处置 |
|---|---|---|---|
| **可锚性三形态判死** | `ANCHORABLE=False` + `why_not_anchored()` 三条理由带实测 | **不需要**：能力模块不产出锚，无"判死"对象 | 不移植（§2） |
| **双层界代替浮点 golden** | `p_max ≤ p_exact ≤ Σp` 等可证双侧界 | 光子侧已是"闭式 golden ⇄ 独立数值 candidate"，判据本身是残差 | 已具备，无需动作 |
| **覆盖分档** | K4 的 L2/L3/盲区 + L4 正交性证明 | K4 已覆盖全账本（含光子 452 道），不需分域 | 已具备 |
| **声明-验证分离** | 声明面（`ANCHORABLE`）与判决面（门禁）分开且互相咬 | **缺**：成对实现靠命名惯例，无机制 | **本版补齐 → G11 / G11b** |

🔴 只有第四条真的有缺口，而它恰好是最重要的一条 —— "写了闭式与数值两半"这件事
本身是**声明**，没有门禁就只是**声明**。这与 F-11（判据存在、证据丢失）、
F-8（纪律门禁存在、K4 看不见）是同一族的第四次出现：

> **凡是"依赖某个惯例才成立"的东西，早晚会在惯例失效时静默退化。**

## 8. 诚实边界

- **A / C 两张清单不是行动项**：它们是形态判据的产物，61 条里绝大多数是设计函数。
  本版**没有**给任何模块补 `ANCHORABLE`，因此"光子侧可锚性声明 0 个"这个数字**保持不变** ——
  那是**判断**（不该补），不是遗漏。
- **G11 只保证"门禁碰到了那对实现"**，不保证门禁**判得对**。它守的是接线不丢，
  不是判据质量；判据质量由各模块自己的门禁负责，本版未逐条复核那 12 道门禁的强度。
- **`lda_agent` 的 2 条零引用是真登记、不是真修好**：`demo_fix` 是 demo 入口、
  `list_designs` 是未被端点暴露的库 API。删/接都是独立决策，本版只让它们**可见**。
- **`ANCHORABLE` 的双语义本版只诊断、未拆解**。拆它要动 11 个模块 + G7/G9 + 3 小时基线，
  收益与风险不成比例；冲突已写进代码注释，留给后续版本决策。
- **F-11 域分布读的是报告里的**标签**（`independence_evidence` 字符串），不是数值。
  报告 float 只留 9 位有效数字，任何"从报告反算残差"的做法都会错（v0.9.280 实测差 6 倍）。
- 本版**未跑全量 core 350**：改动面为 `reachability.py`（扫描面常量）+
  `reachability_registry.py`（基线与契约）+ `run_reachability_smoke.py`（判据）+
  新增只读脚本 + 文档。护栏子集实跑见 CHANGELOG。
