## 二·零、**本次审计最高价值发现：主干 CI 是红的**（已修复）

`run_ci_regression --tag core` 实跑结果：**68 PASS / 1 SKIP / 1 FAIL，总耗时 794.15s**，失败项 `run_webui_api_smoke.py`。

而 README 与 v0.9.0 发布说明均宣称「CI core 70 条全绿」。**对外宣称与实际状态不符——这是审计中最该被抓住的一类问题。**

### 根因（精确到行）

| 层 | 事实 | 证据 |
|---|---|---|
| 现象 | 6 个 GET 端点返回 401 | `/api/admin/config`、`/api/admin/orders`、`/api/admin/users`、`/api/store/me/licenses`、`/api/store/me/summary`、`/api/store/orders/mine` |
| 直接因 | 冒烟脚本用硬编码 dev token `Bearer LDA-ADMIN-DEV-TOKEN-CHANGE-ME` | `run_webui_api_smoke.py:188`（修复前） |
| 根因 | **v0.8.55 安全加固后弱默认令牌已失效**——`is_admin()` 只认环境变量 `LDA_ADMIN_TOKEN` 或 store 内 `is_admin` 用户，硬编码 dev token **永不被接受** | `store.py:350-357` |
| 性质 | **典型的"安全加固打破测试"**：加固本身完全正确，但冒烟脚本未同步适配 → 门禁失真 | — |

### 修复（本次审计已执行）

修复原则：**让 CI 变绿，但绝不降低安全标准**。

1. `admin` 端点：读环境变量 `LDA_ADMIN_TOKEN`（生产必设路径）
2. 需登录端点：临时注册 smoke 专用账号取 token，覆盖真实 200 路径
3. **新增安全回归断言**：需鉴权端点在无任何凭据时若返回 200 → **直接 FAIL**（防将来误关鉴权）

### 修复验证（双路径实测）

| 场景 | 结果 |
|---|---|
| 无凭据 | `PASS=74 · FAIL=0`；admin 端点 =「401 鉴权有效（守护断言）」；`store/me` 端点 = **200 JSON**（真实覆盖） |
| 带 `LDA_ADMIN_TOKEN` | `PASS=74 · FAIL=0`；admin 端点全部 **200 JSON**（真实覆盖） |

**净收益**：实跑 PASS 68 → **74**（新增 6 条鉴权守护断言），FAIL 1 → **0**，且安全断言比修复前更严。

### 1.2 三条核心战略判断

**判断一：技术侧的主矛盾已从"能力有无"转为"验证可信度"。**
46 锚听起来厚实，但拆开看：B 类 27 条（其中 **B5/B6/B7 三条是自证桩**，golden 为"理想下限"而非外部真值，`benchmarks.py:95-104`）、E 类 7 条（语料自述为"示例种子"，`seed_empirical.json:2`）、S 类 12 条（系统级确定性）。**真正能把 AI 求解器"钉在事实地基上"的外部 ground = 7 条种子语料 + 默认断开的 ORACLE**。`lda/ext_oracle/meep_oracle.py` 需手工设置 `LDA_MEEP_PY` 装隔离 Meep 环境才通（`:36-39`），`oracle_sax.py:19` 直接 `return None`，B6 光栅耦合 `_sim_grating` 直接 `return None`（`:184-189`，"预留 Tidy3D，需 API key"）。
→ **外部技术买家来验货时，"双 ground 交叉验证"这条核心卖点当前无法现场演示。** 这是护城河叙事里最脆的一环。

**判断二：商业侧的瓶颈不是货架不够多（58 已过剩），而是价值捕获精度与交付人力。**
本地订单数据说话：**定制需求 13 单 > 直接购买 7 单**（定制占 65%），而 13 个定制单 `amount_cny` **全部为 0**（`quote_later`）；50 个开放货架中，**产生实际订单的只有 1 个**（`IM-CPO-WDM5`，7/7 单）。
市场发出的真实信号是：**"我要你帮我做" > "我要买你的包"**。
→ **继续扩货架是无效功。** 正确动作是：从 13 个定制需求里提炼高频方向 → 产品化为标准货架 → 分层定价。同时统一定价 ¥1999 必须打破（一个 CPO 光引擎预设计 vs 一个 FTTH PLC 分路器同价，复杂价值被系统性低估）。

**判断三：量子侧（双引擎之一）处在"无回归保护"的裸奔状态。**
22 引擎中量子占 7 个、46 锚中量子占 13 条（B9/B10/B12/B13/B17/B18/B22-B27）。但实测：`run_quantum_design` / `run_multiqubit_fidelity` / `run_multiqubit` / `run_readout_chain` / `run_readout_fidelity` 等**量子系 9 个 smoke 全部不在 `CORE_SMOKES`**（`run_ci_regression.py:35-128`）。量子物理定律锚靠 `run_harness.py` 进了门禁，**但量子设计闭环与读出链路（D-46/D-47 集成路径）没有任何 CI 保护**。
→ 任何改动都可能静默破坏量子侧而不被 CI 捕获。**这是全项目性价比最高的补漏项**（成本低、风险高）。

### 1.3 一句话战略建议

> **停止横向扩张（货架冻结在 58），转向纵深：技术侧补"可被外部验货"的硬证据，商业侧补"能自动收钱"的价值捕获，生态侧维持纪律等待发动信号。**

**设计上最关键的一个决定**：解析解用**精确闭式**而非一阶近似。一阶近似给 0.954500、精确解给 0.954413——差异虽小，但用近似去"验证"蒙特卡洛就成了两个近似互相印证，不构成硬 ground。用精确闭式，MC 若有偏会被解析解直接抓出来，锚才具备可证伪性。

## 六·补二、D2 执行结果：三档定价已落地

杜先生拍板三档 **¥599 / ¥1999 / ¥4999**，并授权 AI 依据市场调研确定每个货架的归档。已完成。

| 项 | 结果 |
|---|---|
| 实现 | `lda/lda_webui/shelf_pricing.py`（分档表）+ `store.base_price()` |
| 定价优先级 | 管理员 `config.prices` > 代码分档表 > `DEFAULT_PRICE_CNY` 兜底 |
| 覆盖 | **58/58 全部归档**（开放：599×15 / 1999×18 / 4999×17；量子咨询制 8 项起步价 4999） |
| 端到端实测 | `/api/shelf` 返回价格分布正确 ✅ |
| CI 护栏 | `run_innovation_market_smoke` 新增 7 条定价断言 |
| 全量回归 | **70 PASS / 0 SKIP / 0 FAIL（780.87s）全绿** |
| 策略文档 | `docs/lda_pricing_strategy_2026-08-30.md` |

**分档第一判据是"开源可替代性"**——能否由 gdsfactory 现成标准件直接拼出。判据来源是项目自己的 `lda_l1/gdsfactory_bridge.py:26-38`（8 类标准件映射），是硬证据不是猜测：客户本可免费拿到 → 基础档；有零件无成品 → 标准档；生态完全无现成 → 高端档。

**市场调研锚定了三件事**：
1. 国际 Design House 设计服务：标准 cell €5,500 起、定制 €11,000 起
2. 流片成本：国内无源 MPW ¥6–8 万、有源 ¥13–19 万
3. → LDA 定价为其 **1/10 到 1/100**，这个差距**合理而非过低**（性质差异：对方交付流片级可制造设计，LDA 交付未流片预设计 + 死锚报告）。真正对标的是工程师自研时间成本——设计一个 800G DR8 前端需数周，远超 ¥4999

**一个定价细节**：¥4999 而非 ¥5000，卡在中国企业采购免招标阈值线（多数企业 5000 元以下简易采购）。高端档因此仍可由部门主管直接决策，不必走招投标——显著降低采购摩擦。建议后续调价保持这个特性。

**对审计结论的影响**：R10（统一定价）已解除。但 R11（定制需求占 65% 且金额全为 0）、R16（单人瓶颈）仍在——**定价分档解决的是"标品的价值捕获"，定制侧的报价自动化是另一个独立问题**，需 P1-2 跟进。

## 八、结语（诚实评估）

**做得好的**：主权纪律（GPL 零污染）、红线纪律（LLM 不进判决、C 期锁死）、规模性能（近线性化，千倍提速）、商务闭环完整度、诚实标注文化（"仿真预期·未流片"贯穿全站）——这五条构成了 LDA 的真实可信度基础，比功能数量更值钱。

**做得不够的**：验证可信度的"可演示性"（ORACLE 默认断）、商业模式的"可规模化"（全人工）、量子侧的"可回归性"（无 CI 门禁）——这三条是**从"看起来很强"到"被验证为强"之间必须跨过的坎**。

**核心建议**：下一轮不要用"又新增了什么"来衡量进展，而要用**"又有几条能被外部独立验证"**和**"又有多少环节不再依赖杜先生本人"**来衡量。

**最后一个启示**：本次审计最实在的收获不是发现了多少缺口，而是**跑了一遍全量回归**——正是这一跑，抓出了「README 宣称 70 条全绿、实际 1 FAIL」的失真。文档里的数字如果不定期用机器复核，就会悄悄变成自我安慰。建议把 `--tag core` 全量回归固定为**每次发版前的必跑动作**（13 分钟，成本极低）。
