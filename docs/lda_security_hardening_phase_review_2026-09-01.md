> 编制日期：2026-09-01
> 触发事件：2026-08-31 生产服务器被并发重计算打爆
> 涉及版本：v0.9.4（68dd561 前序）→ v0.9.5（68dd561）→ v0.9.6（aae73fb）→ v0.9.7（6984ef2）
> 状态：三端（本地 / Gitee / GitHub）+ 生产全同步，HEAD = `6984ef2`，生产 `version 0.9.7`、`is-active = active`

---

## 一、事件回顾：发生了什么

2026-08-31，生产服务器出现资源爆表。用户第一反应是怀疑**新做的部署技能出现死循环**（"在没有做上传技能时没这个问题，你做了一个上传部署技能就出这个问题了"）。

这个怀疑是合理的，也必须先排除——如果部署脚本真有死循环，它会反复在服务端拉起进程，比任何代码敞口都危险。

**自检结论：部署脚本无罪。**

| 核查项 | 结果 |
|---|---|
| `remote_deploy.py` 是否含循环/重试 | 无 `while`、无 `retry`，一次性线性流程 |
| 故障期 SSH 连接 | 全部 5 次在 **connect 阶段**失败 |
| 实际执行的服务端命令 | **0 条**（连接未建立，命令无从执行） |
| 结论 | 部署脚本未触发任何服务端负载 |

既然不是部署脚本，负载只能来自**已经跑在生产上的代码**。

---

## 二、根因分析：真正的引爆点

**结构性根因（两个条件叠加才会爆）**

1. `lda/lda_webui/app.py:44` 使用 **`ThreadingHTTPServer`** —— 每个请求一个独立线程，天然支持并行处理。
2. 存在**无鉴权 + 默认实跑重计算**的公开端点 —— 任何人发一个请求，服务端就真的开始算。

两者叠加的结果：并发 N 个请求 = 并行跑 N 个重计算 = CPU / 内存被线性吃满。这不需要攻击者，外部扫描器、监控轮询、反复自测都能触发。

**具体敞口端点**

| 端点 | 方法 | 默认行为 | 危害 |
|---|---|---|---|
| `/api/cpo_array` | GET | 实跑 100,096 器件（build+DRC+LVS，4–8s） | 高并发直接打满 |
| `/api/benchmark_crosscheck` | GET | 实跑 `run_crosscheck(quick=True)`（~9–12s） | 同上 |
| 50 个 `run_*` 仿真/设计端点 | POST | 触发 FDTD / S 参数 / 逆向设计等真实计算 | 同上，且数量更多 |

**一个被讨论挖出的更硬事实**：这 50 个 POST 端点**同样全无鉴权**——handler 内无 token 校验，`app.py` 的 `_dispatch` 也没有统一鉴权闸门。所以"要不要防护"不是锦上添花，而是与打爆服务器同级的真实敞口。

## 三、处置时间线：四步收口

用户要求"先讨论，再行动"，因此每一步都先明确副作用再落地。

### v0.9.4 —— CPO 验货端点三护栏

| 护栏 | 机制 |
|---|---|
| ① 输入硬上限 | `oe≤48 / ch≤96 / lane≤16`，超限 400，防单请求 scale 到 OOM |
| ② 全局串行锁 | `threading.Lock` + 1s 超时，并发拿锁失败返 429，杜绝并行堆叠 |
| ③ 结果缓存 | TTL 120s，同配置重复请求秒回 |

### v0.9.5 —— 补上第二个公开 GET 敞口

`/api/benchmark_crosscheck` 是同类敞口，补齐同款护栏（串行锁 + 缓存）。至此两个公开重计算 GET 全部带护栏。

### v0.9.6 —— 50 个 POST 重计算端点统一并发护栏

**关键设计修正**：用户初选"按端点逐个护栏"。但纯按端点锁只能锁**单端点**——攻击者同时打 50 个不同端点，每端点各 1 并发，仍可达 50 路并行，照样打爆。因此落地为**双锁**：

| 护栏 | 机制 | 解决什么 |
|---|---|---|
| ① 每端点独立串行锁 | 每端点同时至多 1 个计算，并发 429 | 单端点并行堆叠 |
| ② 全局并发上限 | `Semaphore(min(cpu_count, 4))` | **封死"同时打 50 端点"的总并发** |
| ③ 参数哈希缓存 | TTL 120s / 限容 32 条 | 重复请求秒回，防内存膨胀 |
| ④ 入参体积上限 | 256KB，超限 413 | 超大 payload OOM |

仅 `HEAVY_POST_PATHS`（50 个重计算端点）进护栏；鉴权 / 商店 / 生态等轻端点行为完全不变。

### v0.9.7 —— POST 重计算端点登录闸门

把敞口从"**被并发数封顶**"升级为"**须登录才能触发**"：

- 未登录直接 **401**，且不占缓存 / 并发资源；
- `store.user_by_token(token)`（用户会话）或 `_check_admin(headers)`（管理员 Bearer）**任一放行**；
- **GET 验货端点仍无鉴权**，维持"可被外部独立验货"的战略可达性。

## 四、关于方案选择的讨论（用户提问：会不会有副作用）

用户提出的核心疑问是：防护除了计算安全，会不会带来其他坏处？对性能有无影响？

| 原方案 | 副作用（讨论结论） |
|---|---|
| 全局 semaphore ≤ 2 | ① 跨端点耦合，一个慢 FDTD 卡住所有重端点 ② 若阻塞等待无有限队列，线程堆积成**新 DoS** ③ 把合法并行用户串行化 ④ "2" 是无依据的魔数 |
| nginx `limit_req` | 限的是**到达速率**不是**并发**，挡不住"两个间隔发的 30s 长任务"并发；单独用不闭合 |

**最终选择**：不照搬任一原方案，改为「每端点锁（公平、互不阻塞）+ 全局上限（按核数封顶，不拍脑袋）」。三个副作用被消解。

**对性能的实际影响**：当前真实流量 ≈ 0（生产真实用户 1、真实订单 0），**无可感知影响**。唯一代价只出现在"合法用户高并发"场景，而这恰是防护要治理的对象。

## 六、教训沉淀（升为工程铁律）

1. **先排根因，再加防护。** 故障第一反应常是"最近改动的东西有问题"，但必须实测排除。本次用户怀疑部署脚本，实际是已上线代码的敞口——若直接去改部署脚本，真正的问题会继续炸。
2. **`ThreadingHTTPServer` + 无鉴权重计算 = 结构性 DoS。** 每请求一线程，并发即并行吃资源。任何新加的公开端点都必须先过这个检查。
3. **防护方案要先讨论副作用，不能直接照搬。** 用户"先讨论再行动"的要求是对的：全局 semaphore 的跨端点耦合、盲设魔数、合法用户串行化三个副作用，是在讨论中才暴露的。
4. **纯按端点锁封不住总并发。** 锁单端点 ≠ 锁总资源，必须再叠一道全局上限。这是本次最重要的设计修正。
5. **改鉴权必须同步 smoke（v0.8.55 教训）。** 本次先做影响面排查（确认现有 CI 不经 HTTP 调这些端点），再跑 `--tag core` 全量回归，最后才上线——三者缺一不可。
6. **护栏让"保持开放"变安全。** GET 验货端点之所以敢保持无鉴权，是因为并发已被封顶为 1 且有缓存兜底。战略可达性与安全性不必然冲突。

## 七、遗留风险与后续建议

| 项 | 现状 | 建议 |
|---|---|---|
| 默认 dev token 回退逻辑仍在代码 | 生产已配自定义 token（探针证实），但**新部署 / 自建用户若漏配即可被公开绕过** | 生产模式下拒绝使用默认值，或启动时强告警 |
| GET 验货端点仍无鉴权 | 战略取舍，有并发护栏兜底 | 维持；如要收紧属战略决策非安全必选项 |
| 客户端断连不终止服务端计算 | `ThreadingHTTPServer` 固有限制，护栏只封并发不封单次时长 | 长任务可考虑加超时 / 取消机制 |
| 无 per-IP 限流 | nginx `limit_req` 未配 | 作为边缘廉价补充，防洪泛 |
